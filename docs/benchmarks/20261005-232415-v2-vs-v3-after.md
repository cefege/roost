# v2 (Bun/TS) vs v3 (Rust) — speed benchmark after the echo/renderer/boot pass, run 20261005-232415

- Machine: 6 CPUs, Linux 6.12.107+deb13-amd64 x86_64, 1-min load 3.32 at start; Chrome for Testing 151.0.7922.34 (`--headless=new`, 1280×800, fresh profile per round).
- v3: `a5d459ed` — `target/release/roost` + `roost-keeper`, `wasm-release` web bundle (opt-level "z"). v2: `main` `48f6fa2f` — bun 1.3.14 from source, `vite build` SPA.
- Command: `roost-bench prepare`, then `roost-bench run --rounds 3` (3 rounds per stack, alternating v2, v3).
- Isolation: free loopback ports, fresh `HOME`, `ROOST_TERMINAL_PEER_ENABLED=0`; the page names the round's own worker door through the clients' `roost.localWorkerOrigin` override.
- Units: ms. `cpu_ms` is `/proc` utime+stime per role (10 ms ticks); RSS is summed per role. p50/p95 are nearest-rank; usage rows have one value per round, so their p95 is the max.

## Changes since 20261005-193858

- `4d9bbe5e` bench: each echo is split at the frame that produced the paint. `echo_reply_ms` runs from the key frame sent to that frame handled by the page. `echo_paint_ms` runs from there to the paint. The split comes from a CDP WebSocket trace calibrated onto the page clock.
- `f55b6b6a` worker: `terminal_latency` debug stamps on every hop from door input to the cell frame written. No server hop needed a fix: every hop measured p50 0 ms at the logs' 1 ms resolution.
- `92de7581` web-terminal: a delta-batch fold no longer copies the renderer's held history. Measured natively with 2000 history rows: the removed clone cost 19 µs per paint, and the fold now costs 0.67 µs.
- `be5adc23` web: a paint after the first skips the first-cell mark's clock read and its JSON detail.
- `b1db7ffc` web: the wasm is preloaded with the HTML. On a warm navigation its fetch now starts at 17.4 ms (31.6 ms before this pass); resource timing shows one fetch per navigation.
- `0d184314`, `72e6d5cd` web, bench: `identity_complete` and `viewport_enqueue` are now marked, and `cold_nav` records every navigation's boot timeline (`boot_*_ms`).
- `a5d459ed` web: `wasm-release` builds at opt-level "z", kept by the plan's measured rule. Raw wasm went from 5.76 to 4.81 MB and brotli from 1.56 to 1.40 MB. `boot_wasm_to_main_ms` p50 went from 39.8 to 33.7 ms. Echo renderer CPU and `flood_plain_ms` stayed within 1%.

## Findings

- **Echo is unchanged on both stacks**: 31.7 ms p50 each. The reply half is 16.3 ms on v3 and 14.5 ms on v2; the paint half is 13.4 and 15.1 ms. The reply wait is not server time:
  - Worker stamps put door input received → cell frame written at p50 0 ms and p95 1 ms. Key frame sent → door input received is −0.2 ms p50, inside the logs' 1 ms resolution.
  - In a Chrome trace of 30 strokes, the reply's `WebSocketReceive` task ran at +10.9 ms, behind the `BeginMainFrame` (+6.3 to +10.3 ms) that the keystroke itself scheduled.
  - A minimal page with an instant WebSocket echo answered in 1.6 ms p50, with 10–17 ms outliers whenever the reply landed behind a frame.
  - The wait depends on when the key lands within the display frame. A trial run that paused 20 ms after each paint measured the reply half at 12.0 ms p50, against 16.3 ms here. The bench presses each key at a fixed point after the previous paint.
- **Boot (warm, p50 of 12 navigations)**: the wasm fetch runs 17.4 → 53.3 ms, `module_start` is at 87 ms, `identity_complete` at 113 ms, `terminal_mount` at 148 ms, `viewport_accept` at 184 ms and the first applied cells at 192 ms. Warm navigation takes 194.7 ms on v3 against 176.1 ms on v2 (1.11×, was 1.13×). The largest single stage after mount is `viewport_enqueue` → `viewport_accept`, about 36 ms.
- **Renderer CPU is still 1.31× v2 across the echo run** (3310 vs 2520 ms). The fold fix does not show in this metric. The echo scenario runs before the floods, after only a few shell commands, so its renderer holds little history `[INFERENCE]`. The next lever is patching spans in place instead of rebuilding a row's DOM per change (`cell_row/dom.rs`). That is a renderer redesign and is not started.
- **Caveats**: 1-minute load was 3.3 at start (1.0 for the previous run). Sub-frame differences are noise at n=3. On a warm navigation the wasm comes from the HTTP cache and `boot_wasm_fetch_ms` is still about 36 ms; the cause was not investigated.
