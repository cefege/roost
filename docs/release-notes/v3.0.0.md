# Roost v3.0.0

Roost runs Claude Code and terminal sessions on all your machines from one
browser tab. v3 is a rewrite in Rust with a Dioxus web client: one coordinator
holds the account, the paired browsers and the machine roster; each machine
runs a worker that dials it; and each worker's terminals live in a separate
`roost-keeper` process, so a worker or coordinator restart does not kill a
running session. Each release ships two programs per platform, `roost` and
`roost-keeper`, plus one web bundle, every asset with a `.sha256` beside it.

## Install

On the first machine (installs a coordinator and this machine's worker, then
opens a paired browser):

```sh
curl -fsSL https://raw.githubusercontent.com/cefege/roost/v3/install.sh | bash
```

Arguments after `bash -s --` go to `roost quickstart`: `--dry-run` prints the
whole plan and writes nothing; `--coordinator-url https://…` names the HTTPS
front door you run in front of the coordinator.

To add another machine, run `roost add-machine --platform macos|linux [--label NAME]`
on the coordinator (or use Settings → Machines → Add machine) and paste the
line it prints on the new machine. To pair another browser, run
`roost add-browser`.

Health: `roost status` (services, coordinator, front door, worker roster) and
`roost doctor --since 24h` (anomaly digest from logs and the audit log).

## Release channels

- `install.sh` installs the newest **stable** v3 release (no `-rc`). If no
  stable v3 release exists yet, it installs the newest pre-release and says so.
  Set `ROOST_RELEASE_CHANNEL=prerelease` to install pre-releases.
- `roost update` on a stable build considers only stable releases. On a
  pre-release build, or with `ROOST_RELEASE_CHANNEL=prerelease`, it also
  considers pre-releases. It only moves to a strictly greater version
  (semver: `3.0.0-rc.11 < 3.0.0 < 3.0.1-rc.1`), never sideways or down.
- GitHub's "latest release" marker stays on v2's last release, so v2 machines,
  which update from that marker, are not handed a v3 binary. v3's install and
  update never read it.

## Upgrading from v2

v3 runs **beside** v2, not on top of it. Nothing of v2 is stopped, replaced or
written to, so both can run on one machine while you move over:

| | v2 | v3 |
|---|---|---|
| Linux services (`systemctl --user`) | v2's units | `roost3-coord`, `roost3-worker` |
| macOS LaunchAgents | v2's labels | `com.roost.coordinator-v3`, `com.roost.worker-v3` |
| Coordinator data | `RoostCoordinatorV2` | `RoostCoordinatorV3` |
| Worker data | `RoostWorkerV2` | `RoostWorkerV3` |
| Coordinator listener | | `127.0.0.1:4113` |
| Worker local door | `127.0.0.1:4104` | `127.0.0.1:4114` |

Data directories live under `~/.local/share/` on Linux and
`~/Library/Application Support/` on macOS.

`roost import-v2 --from PATH [--dry-run]` carries a v2 coordinator's account,
paired devices and browser keys into the v3 coordinator, read-only on the v2
side. Machines, sessions and history are not carried: machines re-join v3 with
`roost add-machine`. **It must run before anything creates the v3 database** —
`roost quickstart`, and so `install.sh`, creates a fresh account in an empty
database, and the import then refuses it as another install. So on the v2
coordinator's machine, fetch the v3 programs by hand, import, then quickstart
(Linux x64 shown; the other assets are `roost`/`roost-keeper` for macOS arm64,
`roost-darwin-x64`/`roost-keeper-darwin-x64`, `roost-linux-arm64`/`roost-keeper-linux-arm64`):

```sh
mkdir roost-v3 && cd roost-v3
base=https://github.com/cefege/roost/releases/download/v3.0.0
curl -fsSLO "$base/roost-linux-x64" && curl -fsSLO "$base/roost-linux-x64.sha256"
curl -fsSLO "$base/roost-keeper-linux-x64" && curl -fsSLO "$base/roost-keeper-linux-x64.sha256"
sha256sum -c roost-linux-x64.sha256 roost-keeper-linux-x64.sha256   # macOS: shasum -a 256 -c …
mv roost-linux-x64 roost && mv roost-keeper-linux-x64 roost-keeper && chmod +x roost roost-keeper

./roost import-v2 --from ~/.local/share/RoostCoordinatorV2/coordinator_v2.db --dry-run
./roost import-v2 --from ~/.local/share/RoostCoordinatorV2/coordinator_v2.db
./roost quickstart
```

On macOS the v2 database is
`~/Library/Application Support/RoostCoordinatorV2/coordinator_v2.db`. If a v3
coordinator is already running, `import-v2` refuses until it is stopped.

`roost self-link` points `~/.local/bin/roost` at the v3 install. It refuses to
replace a regular file there, which is what v2's `install-binary.sh` wrote;
remove v2's binary when you retire v2.

## Platforms

- **macOS** arm64 and x64 (launchd).
- **Linux** arm64 and x64 with systemd user services; glibc 2.28 or newer.
- **Windows** and every other device: browser only. v3 installs no Windows
  machine.

## Dropped from v2

These are unreachable in an all-v3 fleet and are not in v3:

- the Windows update broker;
- the legacy unimplemented `Sync` server-streaming RPC;
- the legacy `/w/:workspaceId[/t/:channelId]` routes;
- `client-seq.txt`;
- the keeper's Bun ABI identity (a v3 keeper reports the fixed runtime family
  `rust`);
- the Bun-specific zlib workaround;
- capability fallbacks for peers lacking a capability every v3 peer advertises;
- the whole v2 TypeScript product tree (`apps/`, `packages/`, the product
  `scripts/`);
- the Homebrew formula: install with `install.sh`.
